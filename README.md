# Scrivener (Подьячий)

RAG-система для работы с документами, использующая интеллектуальный чанкер [SmartChanker](https://github.com/igorvolk1961/smart_chanker) для создания структурированных чанков с сохранением иерархической структуры документов.

## Основные возможности

- **Интеграция с файловым хранилищем КФО**: Запросы к API Scrivener в продакшн выполняются из low-code скриптов файлового хранилища. Все актуальные конфигурации (включая ключи доступа) хранятся в файловом хранилище, передаются в запросах и кэшируются на стороне сервера Scrivener
- **Система агентов**: Гибкая система агентов с инструментами для работы с RAG, веб-поиском и рассуждениями
- **Поддержка множественных конфигураций**: Одновременно может быть задействовано множество различных конфигураций LLM, эмбеддингов и векторных БД
- **Управление документами**: Добавление, удаление и получение информации о документах в векторной базе данных
- **История чата**: Автоматическое сохранение и загрузка истории диалогов из файлового хранилища
- **Расширение контекста**: Инструменты для горизонтального и вертикального расширения найденных чанков для формирования более полного контекста
- **Абстракция от БД**: Архитектура позволяет использовать различные векторные БД через единый интерфейс

## Технологический стек

- **Чанкер**: SmartChanker
- **RAG Framework**: LlamaIndex
- **Векторное хранилище**: Qdrant (единственный необходимый внешний сервис, но архитектура позволяет использовать другие БД)
- **LLM**: Поддержка любых провайдеров с OpenAI-совместимым API (OpenAI, Ollama и другие)
- **Эмбеддинги**: GigaEmbeddings (GigaChat API) - один из возможных эмбеддеров. На данном этапе реализовано подключение только к нему
- **Backend**: FastAPI
- **Desktop App**: Для отладки в автономном режиме (в разработке)

## Установка

1. Клонируйте репозиторий:
```bash
git clone https://github.com/igorvolk1961/scrivener.git
cd scrivener
```

2. Создайте виртуальное окружение:
```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/Mac
source .venv/bin/activate
```

3. Установите зависимости:
```bash
pip install -r requirements.txt
```

4. Настройте конфигурацию:
   - Файл `config.yaml` используется для настройки порта, по которому осуществляются вызовы Scrivener, настроек логирования и настроек по умолчанию, которые не передаются в запросах
   - Для отладки в автономном режиме используется файл `config_debug.yaml`

5. Сервис Qdrant:
   - При запуске API сервера локальный Qdrant может стартовать автоматически, если в `config.yaml` заданы `qdrant.executable_path` и `qdrant.config_path` и включён `qdrant.auto_start: true`. Если Qdrant уже доступен по `qdrant.url` — автозапуск не выполняется.
   - Иначе запустите Qdrant вручную (локально или удалённо) — это единственный необходимый внешний сервис.

## Использование

### Запуск API сервера

Основной режим работы - доступ по API:

```bash
python main.py
```

или

```bash
uvicorn api.main:app --host 0.0.0.0 --port 8000
```

API будет доступен по адресу `http://localhost:8000`. Документация доступна по адресу `http://localhost:8000/docs`.

### Десктопное приложение

Десктопное приложение предназначено для отладки и тестирования Scrivener в автономном режиме без необходимости подключения к реальному файловому хранилищу КФО.

#### Основные возможности

- **Интерактивный чат**: Отправка запросов к Scrivener API с настройкой режимов работы (интернет, база знаний)
- **Управление RAG**: Полный цикл работы с документами:
  - Загрузка файлов в локальное хранилище эмулятора КФО
  - Индексация документов в векторную БД
  - Управление коллекциями и чанками
- **Эмулятор КФО**: Встроенный эмулятор файлового хранилища КФО, запускаемый на порту 8001
- **Управление пользователями**: Работа с пользователями и сессиями
- **Настройки**: Конфигурация подключения к API Scrivener

#### Структура интерфейса

Приложение построено на базе Tkinter и содержит следующие вкладки:

1. **Чат** - основной интерфейс для взаимодействия с агентом:
   - Настройка режимов работы (интернет, база знаний)
   - Управление информационными объектами (IRV ID, Chat History IRV ID)
   - История диалога с агентом
   - Сохранение истории чата

2. **RAG управление** - управление документами и векторной БД:
   - **Загрузка в хранилище**: Загрузка файлов в эмулятор КФО с созданием IRV ID
   - **Добавление в RAG**: Индексация документов из хранилища в векторную БД
   - **Управление RAG**: Просмотр информации о чанках, удаление документов

3. **Коллекции** - управление коллекциями векторной БД:
   - Просмотр списка коллекций
   - Получение информации о коллекциях
   - Удаление коллекций

4. **Настройки** - конфигурация приложения:
   - URL API Scrivener (по умолчанию `http://localhost:8000`)
   - Сохранение и загрузка настроек

5. **Пользователь** - управление пользователями эмулятора КФО:
   - Создание пользователей
   - Управление сессиями

#### Эмулятор КФО

При запуске десктопного приложения автоматически запускается эмулятор КФО - упрощенная версия файлового хранилища, которая:

- Работает на порту 8001 (по умолчанию)
- Предоставляет REST API, совместимый с реальным КФО
- Хранит данные локально в директории `data/debug_storage/`
- Поддерживает основные операции:
  - Работа с информационными объектами (IRV)
  - Загрузка и получение файлов
  - Управление пользователями и сессиями

Эмулятор позволяет тестировать полный цикл работы с Scrivener без необходимости подключения к реальному КФО.

#### Запуск десктопного приложения

```bash
python desktop/main.py
```

При запуске:
1. Автоматически создается директория `data/debug_storage/` для локального хранилища
2. Запускается эмулятор КФО на порту 8001
3. Открывается главное окно приложения

**Требования:**
- Запущенный API сервер Scrivener (по умолчанию на `http://localhost:8000`)
- Запущенный Qdrant (для работы с векторной БД)

**Примечание:** При закрытии приложения эмулятор КФО автоматически останавливается.

**Подробное руководство пользователя:** См. [DESKTOP_APP_USER_GUIDE.md](DESKTOP_APP_USER_GUIDE.md) для детальных инструкций по использованию всех функций десктопного приложения.

## API Endpoints

### Генерация ответа

**POST** `/v1/generate`

Генерация ответа от LLM с использованием агентов и инструментов.

**Параметры запроса:**
- `current_message` (обязательно) - текущее сообщение пользователя
- `chat_history_irv_id` (опционально) - UUID версии ИО с историей чата
- `result_irv_id` (опционально) - UUID версии ИО для сохранения файла ответа
- `irv_id` (опционально) - UUID версии текущего информационного объекта
- `system_prompt` (опционально) - системный промпт (используется только при пустой истории)
- `temperature` - температура генерации (по умолчанию 0.2)
- `max_tokens` - максимальное количество токенов (по умолчанию 8000)
- `llm_api_key` (обязательно) - API ключ LLM
- `llm_url` (обязательно) - URL LLM API
- `llm_model_name` (обязательно) - название модели LLM
- `internet` - использовать веб-поиск (по умолчанию false)
- `knowledge_base` - использовать базу знаний RAG (по умолчанию false)
- `embed_api_key` (опционально) - API ключ для эмбеддингов
- `embed_url` (опционально) - URL API эмбеддингов
- `embed_model_name` (опционально) - модель эмбеддингов
- `vdb_url` (опционально) - URL векторной БД
- `search_api_key` (опционально) - API ключ для веб-поиска
- `search_url` (опционально) - URL поиска
- `file_irv_ids` (опционально) - список UUID версий ИО со входными файлами

**Ответ:**
- При успехе: объект с полем `content` (текст ответа или распарсенный JSON, если ответ был в формате JSON)
- При ошибке: объект с полями `error`, `detail`, `code`, `errors` (при валидации)

**Особенности:**
- Всегда возвращает HTTP 200, проверяйте наличие поля `error` в теле ответа
- При `internet=false` и `knowledge_base=false` вызывается простой LLM без агентов
- При включении `internet` или `knowledge_base` используется система агентов с соответствующими инструментами
- История чата автоматически сохраняется в файловое хранилище КФО

### Управление файлами в RAG

**POST** `/v1/rag/manage`

Управление файлами информационного объекта в векторной базе данных.

**Параметры запроса:**
- `vdb_url` (обязательно) - URL векторной базы данных
- `irv_id` (обязательно) - UUID версии информационного объекта
- `action` (обязательно) - действие: `"add"`, `"remove"` или `"info"`
- `embed_api_key` (опционально) - API ключ для эмбеддингов
- `embed_url` (опционально) - URL API эмбеддингов
- `embed_model_name` (опционально) - модель эмбеддингов
- `embed_batch_size` (опционально) - размер батча для эмбеддингов
- `max_chunk_size` (опционально) - максимальный размер чанка

**Действия:**
- `add` - файлы docx и txt обрабатываются через SmartChanker и сохраняются в БД
- `remove` - удаляются все чанки, связанные с указанным irv_id
- `info` - получается информация о файле в векторной БД (количество чанков, типы и т.д.)

**Ответ:**
- Объект с полем `content`, содержащим результат операции

### Проверка доступности векторного хранилища

**POST** `/v1/rag/health`

Быстрая проверка доступности векторного хранилища (Qdrant) без выполнения операций с данными.

**Параметры запроса:**
- `vdb_url` (обязательно) - URL векторной базы данных

**Ответ:**
- Объект с полями:
  - `available` - доступен ли сервер
  - `message` - сообщение о статусе
  - `version` (опционально) - версия Qdrant

### Получение списка коллекций

**POST** `/v1/rag/collections`

Получение информации о всех коллекциях в векторной базе данных.

**Параметры запроса:**
- `vdb_url` (обязательно) - URL векторной базы данных

**Ответ:**
- Объект с полем `content`, содержащим список коллекций с информацией о каждой

### Удаление коллекции

**DELETE** `/v1/rag/collections/{collection_name}`

Удаление указанной коллекции из векторной базы данных.

**Параметры:**
- `collection_name` (path parameter) - имя коллекции для удаления
- `vdb_url` (query parameter) - URL векторной базы данных

**Ответ:**
- Объект с полем `content`, содержащим результат операции

### Управление кэшем конфигураций

**GET** `/v1/cache/info`

Получение информации о размере кэша конфигураций.

**Ответ:**
- Объект с полями:
  - `cache_size` - количество закэшированных конфигураций
  - `message` - сообщение о размере кэша

**DELETE** `/v1/cache/clear`

Очистка кэша конфигураций (включая конфигурации LLM, эмбеддингов и других сервисов).

**Ответ:**
- Объект с полем `message` о результате операции

## Система агентов

Проект использует гибкую систему агентов для обработки запросов с использованием различных инструментов.

### Архитектура агентов

- **Базовый агент** (`BaseAgent`) - базовый класс для всех агентов
- **SGR Tool Calling Agent** (`SGRToolCallingAgent`) - агент с поддержкой вызова инструментов и рассуждений
- **Реестр агентов** (`AgentRegistry`) - управление доступными агентами
- **Фабрика агентов** (`AgentFactory`) - создание экземпляров агентов из определений

### Абстракция от векторного хранилища

Проект использует архитектуру с абстракцией от конкретной векторной БД:

- **VectorStoreInterface** - абстрактный интерфейс для работы с векторным хранилищем
- **QdrantAdapter** - реализация интерфейса для Qdrant
- **ChunkRepository** - репозиторий для работы с чанками через абстрактный интерфейс
- Инструменты расширения (`ChunkHorizontalExtensionTool`, `ChunkVerticalExtensionTool`) работают через абстракцию

Такая архитектура позволяет в будущем легко добавить поддержку других векторных БД (Pinecone, Weaviate и т.д.) без изменения кода инструментов.

### Метаданные чанков

Каждый чанк в векторной БД содержит следующие метаданные:

- **`irv_id`** - UUID версии информационного объекта, к которому относится файл
- **`irvf_id`** - UUID файла информационного объекта, идентифицирует конкретный файл
- **`document_id`** - идентификатор документа (обычно совпадает с `irvf_id`)
- **`file_name`** - имя файла
- **`chunk_index`** - порядковый номер чанка в файле
- **`chunk_type`** - тип чанка: `"text"`, `"toc"` (оглавление), `"table"` (таблица)
- **`section_number`** - номер раздела документа (иерархическая структура)
- **`chunk_number`** - номер чанка в разделе
- **`word_count`**, **`char_count`** - статистика по чанку
- **`is_complete_section`** - флаг, указывающий, является ли чанк полным разделом
- Метаданные информационного объекта (`irv_name`, `irv_description`, `irv_attrs`)

Эти метаданные используются для:
- Фильтрации чанков при поиске (по `irv_id`, `irvf_id`, `section_number`)
- Группировки чанков при расширении контекста (по `irvf_id` и `section_number`)
- Формирования иерархического контекста при вертикальном расширении
- Предоставления информации об источниках в ответах агента

### Инструменты агентов

1. **RetrievalTool** - поиск информации в базе знаний через векторный поиск
   - Использует гибридный поиск (векторный + полнотекстовый)
   - Поддерживает реранкинг результатов через внешние запросы
   - Работает с множественными конфигурациями векторных БД
   - Абстрагирован от конкретной БД через интерфейс VectorStoreInterface

2. **ChunkHorizontalExtensionTool** - горизонтальное расширение контекста чанков
   - Заполняет пропуски между имеющимися чанками
   - Добавляет соседние чанки для формирования непрерывного блока текста
   - Работает в пределах одного раздела (section_number)
   - Группирует чанки по `irvf_id` (ID файла) для корректной обработки
   - Вызывается только после RetrievalTool

3. **ChunkVerticalExtensionTool** - вертикальное расширение контекста чанков
   - Добавляет чанки из иерархически связанных разделов (родительские, дочерние, соседние)
   - Формирует полную картину по теме
   - Ранжирует связанные разделы по близости к исходным
   - Группирует чанки по `irvf_id` (ID файла) для корректной обработки
   - Вызывается только после RetrievalTool

4. **QueryParaphraseTool** - перефразирование запросов
   - Генерирует альтернативные формулировки запроса для улучшения поиска
   - Используется для неформальных или расплывчатых запросов

5. **WebSearchTool** - поиск информации в интернете
   - Использует Tavily API для веб-поиска
   - Извлекает релевантный контент с веб-страниц

6. **ReasoningTool** - инструмент для рассуждений и планирования
   - Позволяет агенту анализировать ситуацию и планировать действия

7. **FinalAnswerTool** - инструмент для формирования финального ответа
   - Используется агентом для завершения работы и возврата результата

8. **FinalRAGAnswerTool** - инструмент для формирования финального ответа из базы знаний
   - Используется при работе с RAG
   - Включает информацию об источниках из базы знаний

9. **SynthesizeDocumentTool** - синтез документов по шаблонам
   - Создание отчетов, сводок, анализов по готовым шаблонам

### Конфигурация агентов

Конфигурации агентов передаются в каждом запросе из low-code скриптов файлового хранилища и кэшируются на стороне сервера Scrivener:
- Конфигурация LLM (API ключ, URL, модель, температура и т.д.) - поддерживаются любые провайдеры с OpenAI-совместимым API
- Конфигурация эмбеддингов (API ключ, URL, модель)
- Конфигурация векторной БД (URL, коллекция)
- Конфигурация поиска (API ключ, URL)
- Параметры выполнения (максимальное количество итераций, таймауты)

Все конфигурации (включая ключи доступа) кэшируются по ключу, основанному на параметрах подключения, что позволяет эффективно работать с множественными конфигурациями одновременно.

## Интеграция с файловым хранилищем КФО

Одна из ключевых особенностей проекта - интеграция с файловым хранилищем КФО (Система Информационного Управления).

### Основные возможности

- **Выполнение запросов**: Запросы к API Scrivener в продакшн выполняются из low-code скриптов файлового хранилища
- **Хранение конфигураций**: Все актуальные конфигурации (включая ключи доступа) хранятся в файловом хранилище, передаются в запросах и кэшируются на стороне сервера Scrivener
- **История чата**: История диалогов автоматически сохраняется и загружается из файлового хранилища
- **Управление документами**: Файлы для индексации в RAG загружаются из файлового хранилища по UUID версий информационных объектов (irv_id)
- **Сохранение результатов**: Ответы ассистента могут быть сохранены в файловое хранилище как файлы

### Работа с информационными объектами

- `irv_id` - UUID версии информационного объекта, используется для:
  - Загрузки файлов для индексации в RAG
  - Сохранения истории чата
  - Сохранения файлов с ответами
  - Получения контекста пользователя и объекта

- `irvf_id` - UUID файла информационного объекта, используется для:
  - Идентификации файла в метаданных чанков
  - Группировки чанков по файлам при расширении контекста
  - Фильтрации чанков при поиске и расширении
  - Один информационный объект (`irv_id`) может содержать несколько файлов, каждый со своим `irvf_id`

### Клиент КФО

Клиент `CfxClient` автоматически извлекает информацию о базовом URL и сессии из заголовков HTTP запроса (`referer` и `JSESSIONID` cookie) и выполняет запросы к API КФО для работы с файловым хранилищем.

## Конфигурация

### Файл config.yaml

Файл `config.yaml` используется для:
- Настройки порта, по которому осуществляются вызовы Scrivener
- Настроек логирования
- Настроек по умолчанию, которые не передаются (пока) в запросах

В основном режиме работы все актуальные конфигурации (включая ключи доступа) передаются в запросах из low-code скриптов файлового хранилища и хранятся в файловом хранилище КФО.

Основные секции конфигурации:
- **api**: Настройки FastAPI сервера (порт, хост)
- **logging**: Настройки логирования
- **qdrant**: Настройки векторного хранилища по умолчанию
- **embeddings**: Настройки эмбеддингов по умолчанию (GigaEmbeddings)
- **chunker**: Настройки SmartChanker по умолчанию
- **rag**: Параметры RAG-системы по умолчанию (включая настройки реранкера через внешние запросы)

### Файл config_debug.yaml

Файл `config_debug.yaml` используется для отладки в автономном режиме. Содержит полные настройки для работы без файлового хранилища КФО.

```bash
python utils/check_section_number.py "2.1.2.3.T7" --verbose  # Подробный вывод
```
